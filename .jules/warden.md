## 2026-08-11 — [Redacted PII and OTPs from Logs]
**Data traced:** Emails, phone numbers, and One-Time Passwords (OTPs) logged during authentication flow and generic endpoints.
**Exposure found:** Plaintext OTPs with user identifiers (emails/phone numbers) logged directly in `backend/api/auth.py` and `backend/api/v1/endpoints/auth.py` via `logger.info(f"SECURITY: Generated OTP for {otp_in.identifier} -> {otp_code}")`. PII identifiers were heavily logged in plaintext across other parts of the platform too (like the login route blocking).
**Fix:** Removed the `{otp_code}` from the generated OTP message manually in the auth router. Added a universal `RedactingFormatter` processor to `backend/core/logger.py` that hooks both standard Python string logging and structlog to scrub email addresses (saving just first/last character) and phone numbers (saving only last 4 digits). Ensured that JSON serialized fields bypass this to prevent structural corruption while preserving payload masking handled implicitly by the processor traversal.
**Coverage confirmed:** Tested using script outputs and pytest suite against standard logging and structlog with both explicit string kwargs and JSON payloads, confirming fields are successfully redacted.
**Still exposed elsewhere:** The masked user identifiers (e.g., `j***e@gmail.com`) are still logged for auditing purposes. Depending on local privacy requirements, they may need further hashing. Threat detection logs still store `source_number` natively in DB schemas (not logs), which requires a structural retention/deletion policy for full compliance.
